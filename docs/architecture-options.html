codex-router: architecture options

Four ways to route Codex CLI 0.162.1 per step by complexity tier and activity. The facts come from research.md: source at rust-v0.162.1, five live spikes, and a five-round adversarial review with a Codex peer. Constraints the spikes established:

  • A custom Responses provider reuses the ChatGPT login.
  • Per-step rewrites work only inside one compatibility group (comp_hash 3000 + Responses Lite). gpt-5.5 returns HTTP 400.
  • Encrypted reasoning carries across that group.
  • Prompt cache is per model, so every switch starts cold. With 4 switches in a turn, cache reuse fell from 74 % to 21 %.

Decision (2026-10-13): A, proxy only, no shared core

codex-router is self-contained. There is no router-core package shared with claude-model-router or pi-model-router. UI: a router TUI like the Claude Code /router side panel, plus the routed model in Codex's own footer. No agterm-specific code.

Session layout (footer path verified by source + spike 7, see research.md §4.1):

The launcher codex-router starts the proxy, health-probes it, starts a private codex app-server --listen unix://… with the router provider, then runs codex --remote unix://…. The shared daemon and config.toml stay untouched. Still to check live: two clients on one unix app-server, and the footer repaint during a running turn.

Original recommendation: D (narrow core) + A (proxy behind a profile)

  1. Router core (D), kept narrow. A TypeScript package with the decision contract, classifier client (deadline, retry, breaker), pure policy (votes, hysteresis, escalation, context fit) and cost and cache ports. It has no transport, auth or host message shapes. The Codex adapter, the Claude Mod and the Pi extension each map their transcript into neutral facts.
  2. Codex adapter is a Responses proxy (A).
    • It runs only behind codex -p router, which uses an embedded app-server, so plain codex, the shared daemon, VS Code and the desktop app stay untouched.
    • It rewrites model and reasoning.effort only inside the configured model's group. It never re-routes compaction requests, and it strips openai-model.
    • A launcher starts the proxy and health-probes it before starting Codex.
  3. UI: prototype 1 or 2. Both work with A alone. Prototype 3 needs option B.
  4. Later: B only if routing must cover daemon clients and outage tests pass. C only if Codex stabilises step_model_switching with a real per-step barrier.

The peer's strongest objection: A turns an optional cost optimiser into mandatory transport that carries credentials. Fail-open only helps while the listener is alive, and with unbounded_connection_retries on by default a dead proxy can leave a turn reconnecting indefinitely. Mitigations: keep the proxy opt-in per session (profile), keep the transport path tiny and separate from the classifier, and start phase 2 with fault-injection tests.

Options

AProxy only

A local Responses proxy registered as model_providers.router (requires_openai_auth = true, name ≠ "OpenAI") in a router profile. On each POST it classifies on the first step of a turn, applies policy, rewrites model and effort, and forwards to chatgpt.com/backend-api/codex/responses. GET /models passes through.

  • Sees every request, so it routes per step: 5 requests in a 3-tool turn.
  • One process. No experimental Codex APIs. About 1 ms rewrite cost per 1 MB body.
  • Opt-in per session. Plain codex is never affected.
  • Invisible to Codex: the status line and context window still reflect the configured model, so a context-fit guard is required.
  • The bearer token passes through our process. A dead proxy blocks the session.
  • Depends on internal wire details (Lite header, comp_hash, turn metadata).

BProxy in the daemon + app-server observer

The same proxy, installed as the provider in config.toml so all daemon clients route through it: TUI, exec, VS Code, desktop. An observer connects to the daemon socket (WebSocket over UDS, experimentalApi) and calls thread/resume to subscribe to turns, token usage and names. It can optionally write a route tag into the thread title (prototype 3).

  • One proxy covers every client, which was the brief's original pitch.
  • Real turn boundaries, token usage and thread names come from the app-server, not from parsing requests.
  • Enables the footer tag of prototype 3 (opt-in, persistent rename).
  • Requires editing config.toml. A dead proxy breaks every client, not one session.
  • The observer can't see -p router embedded sessions. Cold-resuming would start a second execution.
  • Experimental APIs plus daemon lifecycle (restarts, reloads) add volatility.

COwn app-server frontend (native switching)

Our client owns the conversation. It sends thread/start with config = {"features.step_model_switching": true}, turn/start with model and effort per turn, and best-effort turn/settings/update per step. Codex itself handles the <model_switch> instructions, compaction with the previous model, and the context window.

  • The most correct switching: Codex recomputes window, tools and compaction, and the status reflects the real model.
  • The token never touches our process. The app-server keeps auth.
  • Per-step steering is best-effort. item/completed is not a barrier, and an update can miss the next sample.
  • Built on an UnderDevelopment flag and experimental APIs.
  • We must rebuild the whole Codex chat UX (approvals, diffs, MCP prompts). Very large effort.

DShared router core + host adapters (combine with A, B or C)

One package holds what the two existing routers duplicate. Each host keeps its own transport and UI. In this layout the Codex proxy, the Claude Mod and the Pi extension are thin adapters.

  • Removes the drift seen today: same tiers and activities, but different thresholds (0.8 vs 0.9 fit), cache models (TTL vs explicit sharing) and policy state (stateful vs stateless).
  • The core is testable without any host, and adapters stay small.
  • Three decisions must be settled first: who owns the classifier wire, TTL vs explicit cache sharing, stateful vs stateless policy. Pi's AGENTS.md forbids local heuristics that Claude relies on.
  • If it grows to include transport, a core bug breaks all three hosts. Keep it narrow.

Codex data for the CacheModel port: cache is per model, effort-neutral, and survives a detour of a few minutes (spikes 3 and 5).

Comparison

Scores: good fair poor. Balanced coupling: risk is high when integration strength, distance and volatility are all high together (Khononov).

If you pick D + A: phase 2 order

  1. Transport first. Minimal proxy with path allow-list, header pass-through, openai-model strip and SSE streaming. Fault tests: kill before bind, before upstream, after the first output item; restart; resume. Never re-send after upstream has started.
  2. Request classification. Separate user steps from compaction, memory and guardian requests. Key state by thread id, turn id and request fingerprint, with no global tier. Pin the decision for retries.
  3. Compatibility groups from the refreshed /models catalog, plus the context-fit guard. Unknown or uncertain means forward the original.
  4. router-core extraction from claude-model-router lib/ (classifier client, contract, policy) with Pi's cumulative selection. Settle the three open conflicts.
  5. UI: hook line plus the chosen prototype. The router TUI runs over a 0600 unix socket.

Open decisions for you:

  • Local vs remote compaction for the router provider. The custom provider has remote off by default; capabilities.remote_compaction = "v2" turns it on.
  • Classifier: Jev, gpt-6-luna decisions, or Ollama.
  • Whether to accept profile-only scope (A) or daemon-wide scope (B).
